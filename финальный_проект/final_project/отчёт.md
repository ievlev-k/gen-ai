
## 1. Задача и данные

### 1.1 Что делаем

Автоматизированная система маршрутизации заявок - хелпдеск помощи по стажировкам и поиску работы в IT для студентов. Вопросы по поиску стажировок, собеседованиям, резюме, зарплатам и карьерным советам - система автоматически ищет ответ в базе знаний, построенной на реальных данных из Telegram-чата, и маршрутизирует: уверенный ответ → автоответ, неопределённый → сортировочный агент.

### 1.2 Источники данных

Исходные данные — экспорт из Telegram-чата **sns_internships** (16 559 сообщений, формат HTML-export, период май 2024 — апрель 2026). База знаний (`knowledge_base.txt`) сформирована с помощью LLM на основе сообщений чата: модель извлекла и структурировала обсуждения по темам (поиск стажировок, собеседования, зарплаты, резюме и т.д.) в 16 статей (~623 строки).

## 2. Система

**Используемые техники:**

1. **Synthetic personas** — 5 студентов с `field_validator` (year 1-4), сгенерировали 25 синтетических тикетов
2. **Hybrid RAG** — поиск в KB через BM25 (ключевые слова) + dense embeddings (смысл), результаты объединяются RRF
3. **LLM-as-judge + ghost detection** — LLM сравнивает ответ с эталонным; отдельный промпт проверяет, реальны ли цитаты в KB или модель их выдумала
4. **Агент с инструментами** — triage-агент классифицирует тикет (10 категорий, 4 приоритета, 3 канала)

**Путь данных:**

```
ticket → RAG (BM25 + dense) → top-5 чанков → LLM-ответ
  ├── conf ≥ 0.7 → автоответ студенту
  └── conf < 0.7 → triage-агент → маршрут (auto / TA / instructor)
                        ↓
                   LLM-as-judge → ghost detection → метрики
```

## 4. Где пайплайн ошибался

### #12 resume_help — 5 ghost-цитат при confidence=0.9

**Вопрос:** «Питон бэк, 2 пет-проекта, 4 курс. Не зовут на собесы, фидбек по резюме.»

**Что ответила система:** дала 4 общих совета из KB — оформляй репозиторий с README, не указывай город в резюме, заполняй анкету подробнее, отбор жёсткий. Модель выдала confidence=0.9, то есть была уверена в ответе.

**Gold-ответ:** просил конкретные формулировки — не «знаю Python», а «реализовал REST API на FastAPI с авторизацией JWT».

**Где модель ошиблась:** система выдернула цитаты из разных тематических чанков KB (про резюме, про анкету Тинькофф, про скрининг) и свела их в один совет. Цитаты реально существуют в KB, но не относятся к вопросу про форматирование описания проектов. Ghost detector нашёл 5 таких неуместных цитат.

---

### #22 resume_help — верный ответ по фактам, FAIL по judge

**Вопрос:** «В Тинькофф на анкету смотрят больше, чем на резюме?»

**Что ответила система:** подтвердила, что анкета решает 50–60% успеха в отборе. Привела пример из чата: кандидат прошёл отбор с 420 из 600 баллов. Конкретных рекомендаций по заполнению нет. Confidence=0.20, потому что модель поняла: полного ответа в KB нет.

**Gold-ответ:** содержал конкретные советы — заполняй анкету максимально подробно, используй слова из описания вакансии, заполни все поля.

**Где модель ошиблась:** KB действительно не содержит пошаговой инструкции «как заполнить анкету». Модель честно указала на это и поставила низкий confidence. Однако judge посчитал ответ неполным, потому что gold содержал рекомендации, которых нет ни в KB, ни в сообщении системы. Это проблема качества KB, а не пайплайна.

---

### #28 education — cross-context галлюцинация, confidence=0.95

**Вопрос:** «Магистратура Тинькофф МФТИ — как отбор?»

**Gold-ответ:** отбор по конкурсу GPA, мотивационному письму и собеседованию. Конкуренция 5–7 человек на место.

**Что ответила система:** «Магистратура МФТИ — прямой путь к трудоустройству. Анкета решает 50–60% успеха. NO HIRE за красные флаги (судимость, конфликт интересов).» Confidence=0.95 — модель была уверена.

**Где модель ошиблась:** это худший тип ошибки — система смешала факты из разных разделов KB. Фраза «анкета решает 50–60%» взята из раздела про стажировку Тинькофф, а не про магистратуру. Фраза «NO HIRE за красные флаги» — из раздела про анкету Яндекса. RAG нашёл 5 чанков, содержащих общие слова «Тинькофф», «МФТИ», «анкета», «NO HIRE», и модель склеила их в связный, но неверный ответ. При этом confidence был высоким, потому что модель видела релевантные чанки и не поняла, что они про разные вещи.

---

### 7 из 15 тикетов — KB пуст

Тикеты #1, 2, 3, 13, 15, 18, 24, 25 (DS-секция на собеседовании в Яндексе, открытые фронтенд стажировки, опыт для HR, психологическая подготовка, правила ML-контеста, результаты скрининга Райффайзен, LRU Cache, LeetCode medium для джуна).

Для всех этих вопросов в KB нет конкретных данных. Система честно ответила «нет информации в контексте», выставила low confidence (0.1–0.4) и через triage-агента направила тикет на TA. Это ожидаемое поведение — KB охватывает общие темы, но не содержит ответов на узкие технические вопросы.

## 5. Выводы

### Что делает

6 из 15 вопросов (40%) она отвечает с высокой уверенностью без участия человека. Остальные 60% — честно признаёт недостаток данных и перенаправляет на ассистента или преподавателя. На неизвестных вопросах система не ломается и не выдумывает ответ: ставит низкий confidence и маршрутизирует на человека.

### Где система не справляется

Главная проблема — частичное покрытие KB. Если в KB есть точный ответ, hybrid RAG находит его. Если информации нет или она неполная, модель достраивает ответ из предобученных знаний и при этом выставляет высокую уверенность (тикет #28: conf=0.95 при перемешанных фактах из разных разделов). 7 из 15 тестовых вопросов вообще не покрываются KB — это недостаток базы знаний, а не пайплайна.

Pass rate низкий (26.7% мягкий judge), потому что качество ответа упирается в качество KB. Judge тоже неточен: разброс между строгим (13.3%) и мягким (26.7%) судьями показывает, что оценка сильно зависит от формулировки.

### Что оставил бы в production

- **Hybrid RAG (BM25 + dense)** — работает, находит релевантные чанки
- **Порог auto-solve с эскалацией** — правильный архитектурный выбор: что система не умеет, то идёт на человека
- **Ghost detection** — единственный работающий способ отлавливать выдуманные цитаты

### Что бы изменил

1. **Fact-check по чанкам** — каждый факт в ответе привязывать к одному чанку. Сейчас модель склеивает факты из разных чанков в связный, но неверный ответ. Привязка «факт → чанк» предотвратит cross-context галлюцинации.
2. **Расширение KB по провалам** — 7 вопросов из 15 не покрываются KB. Заполнение этих пробелов поднимет pass rate больше, чем любая настройка поиска.
3. **Увеличение чанков до 768–1024** — текущий размер 512 режет длинные FAQ-секции, из-за чего контекст обрывается посередине ответа.
