## 1. Валидатор схемы

**Сигнатура:**

```python
VALID_TOOLS = {"get_fx_rate", "get_key_rate", "get_inflation", "calculate"}

def validate_plan(plan: Plan) -> list[str]:
    errors: list[str] = []
    for sq in plan.subquestions:
        for tool in sq.expected_tools:
            if tool not in VALID_TOOLS:
                errors.append(f"SubQuestion #{sq.id}: выдуманный инструмент «{tool}»")
        for dep_id in sq.depends_on:
            if dep_id not in {s.id for s in plan.subquestions}:
                errors.append(f"SubQuestion #{sq.id}: зависит от несуществующего #{dep_id}")
    return errors
```

Встроен в `run_pwc()` сразу после `planner()`. При наличии ошибок вызывается `planner(question, feedback=...)` с указанием невалидных инструментов и списком разрешённых.

1. Выдуманный инструмент: Планировщик может добавить `get_cumulative_inflation` или `get_currency_converter` в `expected_tools` - валидатор отлавливает.
2. Несуществующая зависимость: если `depends_on` ссылается на ID, которого нет в списке подвопросов.

## 3. Замер угодливости Критика

5 битых наборов, N=10 прогонов каждый, T=0.0 vs T=0.7.

| Битый кейс                          | T=0.0, ложных принятий | T=0.7, ложных принятий |
|-------------------------------------|------------------------|------------------------|
| арифметика без calculate            | 0/10                   | 1/10                   |
| выдуманное число                    | 1/10                   | 0/10                   |
| несогласованные данные              | 1/10                   | 4/10                   |
| ответ содержит ошибку               | 0/10                   | 0/10                   |
| непокрытая часть вопроса            | 1/10                   | 2/10                   |
| **Итого**                           | **3/50**               | **7/50**               |

При T=0.7 доля ложных принятий более чем вдвое выше (7/50 против 3/50). Гипотеза подтверждается: шум (T=0.7) не лечит зеркальное соглашение, а наоборот критик при T=0.7 более склонен к ложным принятиям, особенно на кейсах с несогласованными данными (4/10 vs 1/10). При T=0.0 критик более строже.

## 5. Вывод: когда PWC оправдан

PWC-паттерн эффективен для **сложных составных вопросов**, где:
- Нужно 2-4 независимых запроса данных + финальный расчёт → разделение Planner/Worker снижает cognitive load каждого LLM-вызова.
- Критик нужен для отлова галлюцинаций между подвопросами (несогласованные числа, пропущенные части вопроса).

PWC **неэффективен** для:
- **Одношаговых вопросов** (Q4, Q5) - накладные расходы (3+ LLM-запроса вместо 1) не оправдывают качество.
- **Многоповторных паттернов** (Q3, 51 месяц) - Планировщик строит план, который Исполнитель физически не осилит за `max_iter`. Здесь валидатор спасает, возвращая честный "решить не могу".
- **Простой арифметики** - одиночный агент с хорошим system prompt (правило `calculate`) справляется сам.

**Практический совет:** используйте PWC, когда вопрос структурно декомпозируется на 2-4 независимых шага с зависимостями и требует перекрёстной проверки согласованности. В остальных случаях - одиночный агент с валидатором инструментов.
